Project vision

From citizen road reports to autonomous inspection and edge AI.

Road maintenance teams often receive many unstructured reports, images, and requests, but limited budgets make it difficult to decide which damaged areas should be repaired first. RDMO started as a computer-vision and clustering pipeline for filtering, analysing, and prioritising crowdsourced road-damage reports.

The current continuation expands the idea into an active inspection system: a Unity digital twin tests UAV monitoring under traffic occlusion, while a shared-backbone multi-task YOLO model detects road defects and road users. The next stage is to move this perception stack toward edge deployment.

RDMO system architecture

A pipeline for acquisition, perception, prioritisation, and deployment.

The project combines offline road-report analysis, simulated UAV inspection, and deployment-oriented computer vision into one road damage optimisation workflow.

📥

Acquire evidence

Collect citizen reports, road images, simulator frames, UAV views, and metadata for maintenance analysis.

🔍

Understand damage

Segment road regions, detect defects, classify severity-related damage types, and identify duplicated reports.

🧭

Optimise decisions

Cluster nearby reports, prioritise damaged zones, and evaluate UAV inspection policies under occlusion.

Deploy perception

Move from server-assisted inference toward edge-ready models that can run close to the inspection platform.

Current perception module

Shared-backbone perception for the digital-twin continuation.

The digital-twin stage replaces the older crop-classifier perception path with a multi-task model that keeps one shared image encoding and separates coarse detection from road-defect subtype recognition.

640×640 RGB Input image
Executed once YOLO backbone + neck P3 / P4 / P5 feature maps
Detection head Road-defect-general · Person · Car
ROIAlign + subtype head Crocodile Crack · Single Crack · Pothole
Why this matters for RDMO: the perception model produces the structured evidence needed by the optimisation layer: defect type, road-user occlusions, confidence, and bounding boxes. The next step is compressing or exporting this model for practical edge deployment.

Digital twin continuation

Next stage

Toward edge deployment of RDMO perception.

Server today, edge tomorrow

The working prototype keeps the custom ROIAlign branch in Python and exposes a lightweight HTTP contract to Unity. This gives a reliable research baseline before optimizing for ONNX, TensorRT, mobile GPUs, or embedded accelerators.

  • Measure Unity-to-model latency and throughput
  • Export or approximate custom ROIAlign inference for deployment
  • Compress, quantize, or distil the perception stack
  • Evaluate edge accuracy/latency tradeoffs against the server baseline
